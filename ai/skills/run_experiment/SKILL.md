# run_experiment — запуск научного эксперимента

## Обязательные границы

1. **Научный эксперимент запускается только через Prefect.** Единая команда:
   `uv run python -m runtime.pipeline --config <experiment.yaml>`.
   YAML содержит `preparation`, `dataset` и `methods`; схема и примеры — `docs/pipeline.md` и
   `examples/configs/`. Старые отдельные entry points не использовать. Отдельные tool-CLI и прямые
   вызовы training/inference-функций не являются запуском нового эксперимента.
2. **Научные вычисления выполняются на GPU-сервере.** На Mac нельзя обучать модели, делать прогноз,
   запускать Phosphoros, оценивать научные выборки или обрабатывать массовые данные. На Mac можно
   редактировать код и тексты, выполнять git-операции, `--check`, Ruff, mypy, unit-тесты на малых
   synthetic fixtures, просматривать результаты и собирать PDF. Те же synthetic-тесты может запускать CI.

## Порядок

### 1. Зафиксировать протокол

- Записать вопрос, данные и их роли, модель, сиды, метрики, критерий успеха и ограничения в
  `docs/experiment_setup.md` или в новом протоколе эксперимента. Для Euclid F/S участвуют в обучении
  и выборе, N — только в тесте.
- Выбрать новый `output`-корень. Prefect сам создаёт в нём каталог `<flow-run-id>`; старые результаты
  не перезаписываются и не используются как рабочая папка нового опыта.
- Подготовить один YAML эксперимента. Общие входы задаются один раз в `dataset`; операции с
  зависимостями и кешируемые ресурсы описываются в `preparation`. Не создавать отдельные YAML для
  каждой модели и не копировать старый захардкоженный скрипт.

### 2. Проверить код до сервера

```bash
uv sync --frozen
uv run ruff check .
uv run mypy .
uv run --extra tracking python -m unittest discover -s tests
uv run python -m runtime.pipeline --config <experiment.yaml> --check
```

`--check` проверяет схему, фабрики и plugin-ссылки, но не существование научных данных, весов и
нативных ресурсов. Эти условия проверяются адаптерами во время запуска.

### 3. Запустить на сервере

- Запрос пользователя на эксперимент уже разрешает технические стадии внутри зафиксированного протокола:
  preflight, probes, fit/inference/evaluation, выбор GPU, параллельные независимые запуски и обоснованный
  повтор после исправления инфраструктурной ошибки. Отдельно спрашивать разрешение на каждую стадию не
  нужно. Спрашивать только при смене научного scope, лимитов или затрагивании чужих ресурсов.
- Код предпочтительно передаётся через git. Для собственного быстрого эксперимента можно использовать
  `rsync`/`scp` в новый собственный каталог, сохранив source snapshot и конфиг. Общий и чужой checkout не
  изменять. Главное на сервере — не трогать чужое и не занимать сразу все ресурсы; технические решения в
  своей работе выбирать свободно.
  Данные и нативные ресурсы размещаются отдельно по `docs/gpu_server_manifest.md`.
- Проверить отсутствие собственного дубликата, свободную GPU по `nvidia-smi`, память, процессы и
  утилизацию. Не занимать все карты и не трогать чужие процессы.
- Выполнить `uv sync --frozen` в существующем checkout, выбрать карту и запустить один внешний
  процесс в `tmux` с `nice`:

```bash
CUDA_VISIBLE_DEVICES=N nice -n 5 uv run python -m runtime.pipeline \
  --config <experiment.yaml>
```

- Зависимости стадий задаются только внутри Prefect (`preparation.needs`, futures и task graph).
  Отдельные скрипты ожидания файлов-маркеров и ручной запуск следующих стадий не нужны.
- Наблюдать собственные логи и состояние исходного процесса. Здоровый процесс не перезапускать;
  отсутствие PID не считать успешным завершением.

### 4. Принять результат

- Получить настоящий код завершения исходного процесса и убедиться, что ожидаемые выходы существуют.
- Проверить `report.html`, `report-data.json`, `metrics.csv`, `metrics.json`, `config_snapshot/` и
  `methods/<имя>/artifact.json`. Manifest проверяется `verify_artifact_manifest`: относительные пути,
  размеры и SHA-256 должны совпасть.
- Для научного вывода независимо пересчитать метрики по сохранённым ID и предсказаниям на сервере.
  Проверить coverage и общий срез объектов, а не только наличие finite predictions. Изменения модели
  сравнивать на одинаковых данных; bitwise-сверки выполнять на CPU сервера.
- Ошибки и частичные выходы сохранить. Не повторять запуск вслепую, не менять протокол по тестовым
  ошибкам и не повышать лимиты без отдельного решения.

### 5. Скопировать и оформить

- Через `scp`/`rsync` по точным собственным путям скопировать на Mac HTML, metrics/report-data,
  predictions, config snapshot, artifact manifests и нужные итоговые веса. Большие мозаики, штампы,
  промежуточные checkpoints и datasets остаются на сервере.
- Числа для текстов брать только из сохранённых артефактов. Отчёт по эксперименту оформлять skill
  `make_report`, месячный отчёт — `make_monthly_report`. Не выдавать technical smoke за научную
  проверку качества и не называть раскрытую валидацию независимым тестом.

## Запрещено

- Запускать научный расчёт на Mac или мимо `runtime.pipeline`, даже для «быстрой проверки».
- Запускать второй экземпляр того же эксперимента, останавливать чужие процессы или использовать
  `pkill -f`/`killall`.
- Читать метки N для обучения, нормировки, выбора модели или подгонки по ошибкам.
- Перезаписывать прежние runs, вручную исправлять предсказания/метрики или удалять failed receipts.
- Копировать большие научные данные на Mac без отдельной явной необходимости.
