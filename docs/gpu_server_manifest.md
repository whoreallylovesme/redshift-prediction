# Работа на общем GPU-сервере

Сервер общий: им пользуются студенты и кафедра. Цель правил — воспроизводимые научные прогоны,
которые не мешают другим.

## Границы вычислений

- На сервере выполняются обучение, прогноз, оценка научных выборок, Phosphoros и массовая подготовка
  данных. На Mac эти операции не запускаются.
- `--check`, Ruff, mypy и unit-тесты на малых synthetic fixtures можно запускать на Mac и в CI.
  Technical smoke на synthetic fixtures не является научным экспериментом.
- Любой научный эксперимент запускается через
  `uv run python -m runtime.pipeline --config <experiment.yaml>`. Отдельные tool-CLI и прямые вызовы
  training/inference-функций не заменяют Prefect-запуск.

## Самостоятельность и действующее разрешение

- Прямой запрос пользователя на эксперимент или серию экспериментов — уже действующее разрешение на
  обычные технические шаги внутри этого scope: checkout и собственный venv, preflight, GPU probes,
  подготовку данных, training, inference, evaluation, Phosphoros, запуск в `tmux`, выбор свободных GPU,
  остановку собственного процесса и копирование результатов.
- **Не спрашивать повторного разрешения на каждый probe, fit, inference, seed, выбор карты или запуск
  следующей стадии.** Не останавливаться на source-only подготовке, если реальный расчёт уже можно
  выполнить. Не ждать специального «GO» после того, как пользователь поставил задачу.
- После диагностированной инфраструктурной ошибки можно исправить причину и сделать ограниченный повтор
  в прежнем протоколе и бюджете. Вслепую не повторять, но и не превращать каждый повтор в запрос
  человеку.
- Использовать вычислительные ресурсы активно: если полезен GPU, запускать на GPU, а не откладывать работу
  ради CPU-only проверок. Несколько независимых сидов/методов можно выполнять параллельно на свободных
  картах. Preflight должен быть коротким и пропорциональным задаче, без бесконечных status-only раундов.
- Отдельное решение человека нужно только для выхода за scope: смены научного протокола, ролей данных,
  целевой метрики или зафиксированных лимитов; использования запрещённых меток; остановки чужих
  процессов; изменения общего окружения; удаления данных; существенного роста загрузки/диска или передачи
  данных наружу. При сомнении сначала делать bounded probe в допустимых рамках, а не просить approval на
  любое действие.

## Ресурсы

- Аппаратная конфигурация по манифесту: 4× RTX A6000 48 ГБ, 64 ядра, 503 ГБ RAM. Перед запуском
  проверять фактическое состояние, а не полагаться на это описание.
- Обычный прогон начинается с одной подходящей карты. Для параллельных сидов, методов или независимых
  экспериментов можно использовать несколько свободных GPU без дополнительного согласования, оставляя
  разумный запас другим пользователям. Не занимать все карты только потому, что они сейчас свободны.
- Эксклюзивно пустая карта не требуется. Совместное использование допустимо, если по свежему `nvidia-smi`
  достаточно памяти, утилизация позволяет работать и собственный прогон не вытесняет чужой. GPU 0 не
  запрещена, но часто занята; выбор всегда делается по фактическому состоянию.
- Проверить отсутствие собственного дубликата загрузки, обучения или прогноза. Здоровый процесс не
  перезапускать. Блокировка pipeline не заменяет проверку чужих процессов и выбор карты.

## Подключение, код и окружение

- `ssh gpu`; адрес, порт и ключ находятся только в локальном `~/.ssh/config`.
- Работать в собственных каталогах: `<server-root>/repo` или отдельный checkout,
  `<server-root>/datasets`, `<server-root>/experiments/<эксперимент>`. Чужие файлы не менять.
- Код доставлять через git на точный commit. Не редактировать исходники вручную на сервере и не
  копировать отдельные `.py` поверх checkout.
- Python 3.13 через `uv`; `uv sync --frozen` выполняется только в собственном checkout/venv. Общую
  среду, чужие пакеты, системный Python и Docker-демон не менять.
- При создании отдельного CUDA-окружения проверять совместимость драйвера и pinned lockfile. Не
  обновлять Torch/CUDA в работающей общей среде.

## Запуск

- Проверить конфиг командой `--check`, затем выбрать карту и задать `CUDA_VISIBLE_DEVICES=N` явно.
- Долгий внешний процесс запускать в отдельной сессии `tmux` с понятным именем и `nice -n 5`.
- Каждый эксперимент использует новый `output`-корень; Prefect создаёт в нём `<flow-run-id>`. Старые
  результаты не перезаписываются.
- Порядок стадий и повторное использование ресурсов задаются task graph и `preparation.needs` внутри
  pipeline. Ручные скрипты ожидания файлов-маркеров и самостоятельный запуск следующих стадий не нужны.
- Конфиг, `config_snapshot/`, код запуска, логи и hashes входов/выходов сохраняются с результатами.

## Наблюдение и завершение

- Смотреть только свои логи, task states и состояние исходного процесса. Snapshot прогресса не
  гарантирует будущую живость или успешное завершение.
- Для успеха нужны настоящий код завершения 0, ожидаемые выходы, `report-data.json`, метрики и
  проверенные `methods/<имя>/artifact.json`. Отсутствие процесса само по себе ничего не доказывает.
- Научные метрики независимо пересчитывать на сервере по сохранённым ID и предсказаниям. Проверять
  общий срез и coverage.
- Не трогать чужие процессы. `pkill -f` и `killall` запрещены; останавливать только свой точный PID
  после проверки identity.

## Ошибки

- Логи, failed receipts и частичные выходы сохраняются.
- Сначала найти причину, затем исправлять; не повторять вслепую, не менять научный протокол по
  тестовым ошибкам и не повышать лимиты без отдельного решения.

## Данные и копии

- Большие данные, мозаики, штампы, промежуточные checkpoints и datasets остаются на сервере.
- На Mac копируются малые результаты: HTML, metrics/report-data, predictions, config snapshots,
  artifact manifests и необходимые итоговые веса. Копирование — `scp`/`rsync` по точным собственным путям.
- Токены, ключи и пароли не попадают в команды, логи, репозиторий и документы.
