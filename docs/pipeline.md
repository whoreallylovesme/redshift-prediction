# Запуск эксперимента

Пути в рецептах отсчитываются от корня checkout. Два маленьких примера запускаются со свежего клона. Для научных рецептов требуются каталоги, указанные в YAML.

| Пример | Что делает |
| --- | --- |
| [regression.yaml](../examples/configs/regression.yaml) | Обучает Ridge и случайный лес по включённой в Git таблице, сравнивает прогнозы для общих ID |
| [fusion.yaml](../examples/configs/fusion.yaml) | Обучает Lightning-модель на снимках NPZ и двух числовых признаках, оценивает её на отдельном каталоге |
| [phosphoros.yaml](../examples/configs/phosphoros.yaml) | Вызывает Phosphoros Core для F_VALID. В рецепте модели укажите пути к локальной установке и подготовленным ресурсам |

Свой эксперимент можно хранить в любом каталоге и передавать в `--config`. Для повторного использования групп в YAML поддерживаются Hydra `defaults`, интерполяции OmegaConf и переопределения аргументами `key=value`. Например, `uv run python -m runtime.pipeline --config examples/configs/regression.yaml workers=1`. Команда `--check` собирает тот же flow, применяет переопределения CLI и проверяет схемы Pydantic, ссылки на рецепты и подключённые функции. Ей не нужны GPU и научные наборы данных.

## Воспроизведение запуска

У нового flow в каталоге результата есть `config_snapshot/`. Исторический flow складывает снимки в `<runs_root>/config_snapshots/<flow-run-id>/`. В `flow.yaml` сохранён собранный рецепт с параметрами командной строки, в `effective.json` видны и значения по умолчанию. Манифест содержит SHA-256 файлов. При включённом MLflow снимок доступен и среди артефактов. Данные, веса и сама установка Phosphoros нужны отдельно.

Из рабочего каталога с данными восстановите файлы, на которые ссылается рецепт, затем передайте сохранённый flow в обычную команду запуска. Утилита сверяет контрольные суммы и сообщает о конфликтах с существующими файлами.

```bash
uv run python -m lib.config.snapshot /path/to/config_snapshot --workspace .
uv run python -m runtime.pipeline --config /path/to/config_snapshot/flow.yaml --check
uv run python -m runtime.pipeline --config /path/to/config_snapshot/flow.yaml
```

## Исторические рецепты

Для запуска прежнего протокола возьмите конфигурацию из артефактов соответствующего эксперимента. Рецепты Teddy/Happy, CapsNet, Euclid Q1 и Phosphoros, существовавшие до очистки, также доступны в [зафиксированной версии Git](https://github.com/whoreallylovesme/redshift-prediction/tree/1f752b82a7f1f54ca74280ae4d85e1264105fdf6/configs). В свежем checkout их можно извлечь с исходными путями. Ключ `-k` защищает существующие файлы от перезаписи.

```bash
git archive 1f752b82a7f1f54ca74280ae4d85e1264105fdf6 configs tests/fixtures/forest.yaml | tar -xk
uv run python -m runtime.pipeline --config configs/flows/capsnet_teddy.yaml --check
```

## Границы модулей

В `lib/workflow/` лежат подготовка таблиц, оркестрация, оценка и публикация результатов. В `lib/train/`, `lib/models/` и `lib/inference/` лежат CapsNet, табличные и визуальные энкодеры, модули регрессии, sklearn и Lightning. В `lib/report/` находятся расчёт покрытия, парные сравнения и HTML. По умолчанию задача использует MAE, RMSE и R².

В `photoz/` находятся адаптеры каталогов и изображений, правила отбора и нормализации для астрономии, целевые преобразования и протоколы обучения CapsNet и Euclid, физические метрики, научные рисунки и адаптер Phosphoros. Старые импорты из `lib/` и вспомогательные CLI делегируют этим модулям. Добавление другого эксперимента начинается с рецепта. Новый критерий оценки подключается через поле `task`, которое принимает `module:symbol` с экземпляром `ReportTask`.

## Схема конфига

```yaml
name: Regression example
output: runs/regression_example
workers: 2
dataset:
  source: tests/fixtures/regression.csv
  id_column: sample
  target: response
  features: [length, width]
  split_column: split
methods:
  ridge: {kind: tabular, recipe: examples/configs/models/ridge.yaml}
  forest: {kind: tabular, recipe: examples/configs/models/forest.yaml}
```

- `dataset` задаёт источник, цель, признаки, ID, при необходимости вес и названия выборок. Можно сослаться на каталог признаков через `feature_catalog` и `feature_set`. Поле `evaluation_files` принимает именованные внешние таблицы, в том числе без столбца цели. CSV-идентификаторы по умолчанию сохраняются строками, включая ведущие нули. Для числового внешнего эталона укажите `csv_id_type: int64`. Без исходного ID встроенный табличный загрузчик помечает строки хешем источника и номером строки.
- `kind: tabular` подключает sklearn-рецепт. `kind: lightning` задаёт тренировочный рецепт и отображение `predict_on` для отдельных каталогов и сплитов. `kind: external` вызывает явно настроенный Python-адаптер, которому передаются рецепт, директория результата и параметры. `kind: saved` подключает готовые прогнозы через `predictions`.
- `methods.<имя>.report` сопоставляет поля прогноза, ID, эталона, статуса, интервала, истории и срезов. Если метки живут отдельно, задайте `reference`, `reference_id_column` и `reference_truth_column`. При сравнении двух методов проверяются уникальность ID и согласованность эталона. Разные выборки сравниваются отдельно.
- `--check` проверяет схему, ссылки на рецепты, имена фабрик и подключаемые функции без запуска обучения. Нативные ресурсы, веса, содержимое наборов данных и научные условия допуска проверяются адаптерами во время работы.

## Prefect и MLflow

Граф состоит из подготовки, обучения каждого метода, зависимых прогнозов, общей оценки и публикации. `workers` или `--workers` задаёт число независимых задач в работе. `threads_per_method` ограничивает поддерживаемые потоки табличных оценщиков. Вызовы Lightning и методы с `resource: accelerator` занимают локальную блокировку на пользователя. При распределённом развёртывании распределение GPU между машинами задаётся инфраструктурой.

Для табличного обучения ключ кеша зависит от **содержимого** подготовленной обучающей выборки, признаков, цели, весов, рецепта, задачи, кода и окружения. Совпадение восстанавливает модель, из которой в новом каталоге заново создаются прогнозы и файлы. Для оценки хешируются прогнозы и доступные внешние эталоны и истории. `cache: false` отключает повторное использование вычислений. Нативный движок, обучение и прогноз Lightning, материализация файлов и запись в MLflow выполняются явно. У исторического Euclid-протокола отдельные правила возобновления по имеющимся результатам.

Каждый новый experiment создаёт каталог `output/<prefect-flow-run-id>/`. При повторной попытке того же flow создаётся вложенный каталог попытки. В `experiment.json` сохранён рецепт, в `tracking.json` — идентификаторы MLflow. В интерфейсе Prefect видны стадии, состояния кеша и таблица итоговых метрик. Результат метода может содержать диагностическую ошибку, при этом отчёт показывает и методы, которые успели завершиться.

MLflow включается параметром `--tracking-uri`, полем `tracking_uri` или переменной `MLFLOW_TRACKING_URI` при запуске CLI. Для каждого метода создаётся run с привязкой к Prefect. Клиент записывает рецепт и метрики по сплитам, Lightning пишет значения по эпохам в тот же run. Отдельный сервер нужен при выборе сетевого URI. Для локального примера достаточно SQLite и extra `tracking`. Сводная таблица и автономный HTML сохраняются и при выключенном трекинге.

## Что попадает в отчёт

`report.html` содержит Plotly целиком и открывается офлайн. Таблица показывает метрики по всем методам и сплитам, включая валидацию, пропуски и ошибки. Для одного метода доступны распределения и остатки, для пары — покрытие и точное пересечение ID. При наличии соответствующих данных доступны кривые обучения, срезы, интервалы, калибровка, примеры ошибок и распределения отдельных объектов. Метрики используют все допущенные строки. Для интерактивного просмотра число отображаемых точек ограничено. Роль внешнего каталога (`truth` или `agreement`) следует задавать по происхождению меток.

`metrics.csv` и `metrics.json` содержат результаты для анализа, `report-data.json` позволяет заново собрать HTML без обучения, исходных каталогов и MLflow.

```bash
uv run python -m runtime.pipeline --render runs/regression_example/<flow-run-id>
```

## Назначение слабых меток Euclid

Команда ниже использует [исторические рецепты](#исторические-рецепты).

`photoz.data.weak_targets.assign_weak_targets` принимает кандидатов PHZ и Hα после отбора по качеству, список неоднозначных SPE ID, исключения независимого теста по ID и тайлу и явных владельцев валидационных объектов. Для Hα вес равен 1, для PHZ — 0.3. У объекта с обоими типами меток приоритет имеет однозначная Hα. Для выборки `large` действует дополнительное исключение всех известных DESI ID из обеих групп кандидатов.

```bash
uv run python -m photoz.data.weak_targets \
  --recipe configs/photoz/large_prepared.yaml \
  --sources configs/photoz/weak_label_sources.yaml \
  --output runs/large-targets/manifest.parquet
```

Для выборки `weak` укажите `configs/photoz/weak_prepared.yaml`. Рецепту нужны каталог PHZ с `object_id, tile, phz_median`, каталог Hα с `object_id, tile, spe_z` и список неоднозначных `object_id`. Файлы протокола содержат принадлежность к валидационной и тестовой выборкам. Для `large` дополнительно нужны `fitting_excluded_ids.parquet` и `all_desi_identity_exclusions.parquet`. Пути к этим данным отсчитываются от соответствующего YAML. Команда проверяет контрольные суммы и записывает новый манифест с ID, тайлом, меткой, источником, весом и разбиением. Для обучения рецепты `weak_prepared` и `large_prepared` принимают фотометрию MER и сверяют её с замороженным манифестом.

## Phosphoros

В рецепте `phosphoros.yaml` опция `include_posterior` добавляет распределение каждого успешно обработанного объекта в Parquet, а `report_from_predictor` передаёт его отчёту с осью из заголовка FITS. В HTML доступны примеры распределений. Если подключён эталон, отчёт также показывает эмпирическое покрытие интервалов.

[Phosphoros Core](https://phosphoros.readthedocs.io/) — отдельная программа на C++ для подбора спектральных шаблонов. Python-адаптер `photoz.methods.phosphoros:predict` выбирает профиль полушария и вариант калибровки, проверяет входной FITS, таблицу запрошенных ID и сетки, вызывает `PhosphorosComputeRedshifts` и читает результат. В общей таблице сохраняются ID, применимость, статус PDF, точечный прогноз и границы интервала. Полный вывод Core остаётся в каталоге метода.

Для полноценного Q1 нужны исполняемые файлы, AuxiliaryData, соответствующая пара сеток и подготовленная фотометрия. Команды подготовки и конкретные ресурсы перечислены в [протоколе Euclid](euclid_q1/README.md). Пример F_VALID допускает прогнозы без меток. Для оценки качества подключите таблицу эталонов по ID через `report.reference`. При наличии заранее рассчитанных прогнозов используйте `kind: saved` для нового сравнения без вызова бинарника.
