# Запуск эксперимента

В YAML один блок `dataset` задаёт входы всех методов. Пути к данным отсчитываются от рабочего каталога. Примеры отличаются набором данных и используют одну схему.

| Эксперимент | Источник и результат |
| --- | --- |
| [TEDDY](../examples/configs/teddy.yaml) | Фотометрия из каталога A, проверка на B. CatBoost использует признаки, CapsNet получает соответствующие им изображения. Укажите подготовленные Parquet с ID `id` и каталоги шестиканальных NPZ, названных по SDSS ObjID. [Описание исходных каталогов](https://github.com/COINtoolbox/photoz_catalogues/blob/master/Teddy/README.md) |
| [Euclid F_VALID](../examples/configs/euclid.yaml) | Секция данных указывает корень подготовленной фотометрии, секция метода задаёт рабочий каталог Phosphoros, конфиг Core и способ получения PDF |

Свой эксперимент можно хранить в любом каталоге и передавать в `--config`. Для повторного использования групп в YAML поддерживаются Hydra `defaults`, интерполяции OmegaConf и переопределения аргументами `key=value`. Например, `uv run python -m runtime.pipeline --config examples/configs/teddy.yaml workers=1`. Команда `--check` собирает тот же flow, применяет переопределения CLI и проверяет схему Pydantic, имена моделей и подключённые функции. Ей не нужны GPU и научные наборы данных.

## Конфигурация запуска

Prefect создаёт `output/<flow-run-id>/config_snapshot/`. В `flow.yaml` хранится конфигурация после применения переопределений, в `effective.json` — параметры с их значениями по умолчанию. Для каждого обучаемого или внешнего метода в `resolved/` сохраняются параметры, переданные реализации. Контрольные суммы перечислены в `manifest.json`. При включённом MLflow снимок доступен среди артефактов запуска. Сохранённый `flow.yaml` можно передать обычной команде `--config` из рабочего каталога, в котором доступны те же данные и ресурсы.

## Границы модулей

В `lib/workflow/` лежат подготовка таблиц, оркестрация, оценка и публикация результатов. В `lib/models/nn/` лежат нейросети и их фабрики, например `lib.models.nn.factories.capsnet`. В `lib/models/tabular/` находятся sklearn-совместимые оценщики и фабрики, например `lib.models.tabular.factories.catboost`. Обучение и прогноз используют `lib/train/` и `lib/inference/`. В `lib/report/` находятся расчёт покрытия, парные сравнения и HTML. По умолчанию задача использует MAE, RMSE и R².

В `photoz/` находятся адаптеры каталогов и изображений, правила отбора и нормализации для астрономии, целевые преобразования и протоколы обучения CapsNet и Euclid, физические метрики, научные рисунки и адаптер Phosphoros. Нейросети с предметной схемой входов находятся в `photoz/models/nn/`, включая Euclid CLIP и табличный ResMLP. Научные функции для новых Python-сценариев импортируются прямо из `photoz/`. Добавление другого эксперимента начинается с рецепта. Новый критерий оценки подключается через поле `task`, которое принимает `module:symbol` с экземпляром `ReportTask`.

Для собственного PyTorch-датасета `lib.dataloaders.hdf5_rows.HDF5Rows` даёт доступ к строкам массива по пути внутри HDF5. Ключ выбирает вызывающий код. Например, признаки и цель разной размерности из одного файла можно подать в стандартный `DataLoader` следующим образом.

```python
from torch.utils.data import DataLoader, StackDataset

from lib.dataloaders.hdf5_rows import HDF5Rows

features = HDF5Rows("measurements.h5", "sensors/features")
target = HDF5Rows("measurements.h5", "sensors/temperature")
batches = DataLoader(StackDataset(features, target), batch_size=32)
```

Адаптер `photoz.data.hayat.HayatDataset` использует этот же ридер для массива `images`. Он задаёт порядок каналов, масштабирование и соответствие между изображением и метками.

Табличный Transformer с маской наблюдений, проекция CLIP и преобразование ограниченной числовой цели доступны в `lib/models/nn/`. Для обучения по отрицательному логарифму правдоподобия используется `lib/train/likelihood.py`. В адаптерах Euclid заданы конкретные полосы, их описания и протокол разбиения. Чтение массива NPZ, нормировка каналов и повороты изображений доступны в `lib/dataloaders/` для любых CV-датасетов.

## Схема конфига

```yaml
name: Photometry benchmark
output: runs/photometry
dataset:
  source: catalogs/train.parquet
  evaluation_files: {held: catalogs/held.parquet}
  id_column: object_id
  target: z_spec
  features: [g, r, i]
  images: stamps
  image_size: 64
methods:
  catboost:
    kind: tabular
    model: catboost
    params: {iterations: 100}
    train:
      split: {val_size: 0.1, shuffle: true, random_seed: 42}
      hyperopt: {enabled: true, cv: 3, scoring: neg_root_mean_squared_error, n_jobs: 1}
      param_grid: {model__depth: [4, 6]}
  capsnet:
    kind: lightning
    model: capsnet
    params: {image_channels: 3, input_size: 64}
    train: {epochs: 10, batch_size: 32, lr: 0.0005}
```

- `dataset.source` принимает CSV, Parquet или Hydra-фабрику с полем `_target_`, возвращающую DataFrame либо объект с атрибутом `.frame`. Фабрику можно использовать с уже установленным поставщиком данных. Для файлов с собственным форматом задайте `reader: module:function`. В выборе обучающей и оценочной частей участвуют `evaluation_files`, `split_column` или параметры случайного разбиения. Табличные и нейросетевые методы читают одинаковые подготовленные строки. Для изображений нужны ID, совпадающие с именами NPZ.
- `dataset.images` может быть общей директорией или отображением `{train: ..., held: ...}`. Совместной модели изображений и таблиц задайте `use_features: true`. Если требуется исходный целочисленный тип ID при чтении CSV, используйте `csv_id_type: int64`.
- В каждом методе `kind` выбирает способ исполнения, `model` указывает реализацию, `params` задаёт её параметры. У Lightning блок `train` задаёт число эпох, размер батча и оптимизацию. У внешнего адаптера `options` определяет конкретный вызов, например набор объектов и выдачу PDF. Нативный `.conf` Phosphoros читает сам Core. Источник из секции данных можно подставить через `${dataset.source}`.
- Для сравнения готовых прогнозов укажите `kind: saved` и `predictions`. При сравнении с внешним методом свяжите тот же сплит через `report.reference: ${dataset.evaluation_files.held}`, указав ID и столбец эталона.
- `methods.<имя>.report` сопоставляет поля прогноза, ID, эталона, статуса, интервала, истории и срезов. Если метки живут отдельно, задайте `reference`, `reference_id_column` и `reference_truth_column`. При сравнении двух методов проверяются уникальность ID и согласованность эталона. Разные выборки сравниваются отдельно.
- `--check` проверяет схему, имена фабрик и подключаемые функции без запуска обучения. Нативные ресурсы, веса, содержимое наборов данных и научные условия допуска проверяются адаптерами во время работы.

В табличном методе `train.split.val_size` задаёт долю обучающего каталога для внутренней валидации. При значении `0` весь каталог идёт на обучение. `shuffle` управляет перемешиванием, `random_seed` фиксирует случайное разбиение. Независимые каталоги из `dataset.evaluation_files` участвуют в оценке после обучения.

При `train.hyperopt.enabled: true` по обучающей части запускается `GridSearchCV`. Параметр `cv` задаёт число разбиений, `scoring` — имя метрики sklearn, `n_jobs` — параллелизм поиска. В `train.param_grid` ключи записываются в формате sklearn Pipeline. Например, `model__depth: [4, 6]` сравнивает две глубины CatBoost. Лучшие параметры и результат на внутренней валидации входят в `methods/<имя>/train_report.json`.

## Prefect и MLflow

Граф состоит из подготовки, обучения каждого метода, зависимых прогнозов, общей оценки и публикации. `workers` или `--workers` задаёт число независимых задач в работе. `threads_per_method` ограничивает поддерживаемые потоки табличных оценщиков. Вызовы Lightning и методы с `resource: accelerator` занимают локальную блокировку на пользователя. При распределённом развёртывании распределение GPU между машинами задаётся инфраструктурой.

Для табличного обучения ключ кеша зависит от **содержимого** подготовленной обучающей выборки, признаков, цели, весов, рецепта, задачи, кода и окружения. Совпадение восстанавливает модель, из которой в новом каталоге заново создаются прогнозы и файлы. Для оценки хешируются прогнозы и доступные внешние эталоны и истории. При заданной `thumbnail_column` отчёт заново читает изображения, чтобы показать изменения в файлах миниатюр. `cache: false` отключает повторное использование вычислений. Нативный движок, обучение и прогноз Lightning, материализация файлов и запись в MLflow выполняются явно.

Каждый эксперимент создаёт каталог `output/<prefect-flow-run-id>/`. При повторной попытке того же flow создаётся вложенный каталог попытки. В `experiment.json` сохранён рецепт, в `tracking.json` — идентификаторы MLflow. В интерфейсе Prefect видны стадии, состояния кеша и таблица итоговых метрик. Результат метода может содержать диагностическую ошибку, при этом отчёт показывает и методы, которые успели завершиться.

MLflow включается параметром `--tracking-uri`, полем `tracking_uri` или переменной `MLFLOW_TRACKING_URI` при запуске CLI. Для каждого метода создаётся run с привязкой к Prefect. Клиент записывает рецепт и метрики по сплитам, Lightning пишет значения по эпохам в тот же run. Отдельный сервер нужен при выборе сетевого URI. Для локального примера достаточно SQLite и extra `tracking`. Сводная таблица и автономный HTML сохраняются и при выключенном трекинге.

## Что попадает в отчёт

`report.html` содержит Plotly целиком и открывается офлайн. Таблица показывает метрики по всем методам и сплитам, включая валидацию, пропуски и ошибки. Для одного метода доступны распределения и остатки, для пары — покрытие и точное пересечение ID. При наличии соответствующих данных доступны кривые обучения, срезы, интервалы, калибровка, примеры ошибок и распределения отдельных объектов. Метрики используют все допущенные строки. Для интерактивного просмотра число отображаемых точек ограничено. Роль внешнего каталога (`truth` или `agreement`) следует задавать по происхождению меток.

Для 95%-го интервала разницы метрик укажите `bootstrap_replicates` в эксперименте и `report.group_column` хотя бы у одного из двух методов. Если группа указана у обоих методов, её значение должно совпадать для каждого общего ID. Отчёт выбирает с возвращением целые группы. Обе модели получают одни и те же строки каждого повтора. Для оценки нужны как минимум две группы и два повтора. [Параметры SciPy bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)

В научном протоколе Euclid единицами выборки служат тайлы и сидовые реализации моделей. Методы с одинаковым числом сидов в сравнении HETDEX получают одну выборку сидов. SciPy выполняет по одному повтору за раз, чтобы сохранить порядок генератора. Границы интервала задают процентили 2,5 и 97,5. При калибровке нуль-пунктов одни и те же кратности тайлов применяются ко всем полосам и обеим итерациям. [Протокол Euclid](euclid_q1/README.md)

`metrics.csv` и `metrics.json` содержат результаты для анализа, `report-data.json` позволяет заново собрать HTML без обучения, исходных каталогов и MLflow.

```bash
uv run python -m runtime.pipeline --render runs/teddy/<flow-run-id>
```

## Phosphoros

В примере `euclid.yaml` опция `include_posterior` добавляет распределение каждого успешно обработанного объекта в Parquet, а `report_from_predictor` передаёт его отчёту с осью из заголовка FITS. В HTML доступны примеры распределений. Если подключён эталон, отчёт также показывает эмпирическое покрытие интервалов.

[Phosphoros Core](https://phosphoros.readthedocs.io/) — отдельная программа на C++ для подбора спектральных шаблонов. Python-адаптер `photoz.methods.phosphoros:predict` выбирает профиль полушария и вариант калибровки, проверяет входной FITS, таблицу запрошенных ID и сетки, вызывает `PhosphorosComputeRedshifts` и читает результат. В общей таблице сохраняются ID, применимость, статус PDF, точечный прогноз и границы интервала. Полный вывод Core остаётся в каталоге метода.

Для полноценного Q1 нужны исполняемые файлы, AuxiliaryData, соответствующая пара сеток и подготовленная фотометрия. Команды подготовки и конкретные ресурсы перечислены в [протоколе Euclid](euclid_q1/README.md). Пример F_VALID допускает прогнозы без меток. Для оценки качества подключите таблицу эталонов по ID через `report.reference`. При наличии заранее рассчитанных прогнозов используйте `kind: saved` для нового сравнения без вызова бинарника.
